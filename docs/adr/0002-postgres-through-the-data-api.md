# 2. Aurora PostgreSQL through the RDS Data API, not DynamoDB

Date: 2026-10-15

## Status

Accepted. Deviates from uselets ADR-0002 (one DynamoDB table per service). Amended by ADR-0025: the
cluster is in the root `template.yml`, and the migrations are applied by the stack's `Deploy` custom
resource. Amended by ADR-0027: no row is read with a Yjs document, and the local `pg` wire refuses a
result over the Data API's 1 MiB.
Amended by ADR-0035: the cluster pauses when idle, and the client sends a statement again while it
resumes, within the wait its caller allows.

## Context

uselets stores everything in DynamoDB with single-table design. JiraIA's MVP needs things that
design cannot give without a second store: filters on any field including custom fields, "moved to
state X after date D", global full-text search over cards, comments and pages, semantic search, bulk
actions, and a board of 20,000 cards opening in under two seconds (escopo-mvp 3.4, 3.6, 3.8, 3.11, 8.1).
DynamoDB plus OpenSearch would answer it with two stores to keep in sync and a high fixed cost.

uselets ADR-0005 also keeps every Lambda out of a VPC. A Postgres reached over TCP would undo that.

## Decision

One Aurora PostgreSQL Serverless v2 cluster per environment (`infra/platform`), Postgres 16 with
pgvector, reached by every Lambda through the **RDS Data API**: HTTPS with IAM, no VPC attachment, no
connection pool to exhaust. Drizzle ORM maps the schema, with the `aws-data-api/pg` driver in AWS and
`node-postgres` against local containers; repositories are written once against `PgDatabase`
(`packages/db`).

Each service owns one Postgres **schema** (`work`, later `pages`, `agents`…), the relational version
of "no service reads another service's table" (ADR-0003). Migrations are generated by `drizzle-kit`,
committed per service, shipped inside the service's package and applied by its `migrate` function.

## Consequences

- One store answers relational queries, full-text (`tsvector`) and vectors.
- The Data API adds latency per statement compared with a pooled connection; board queries must be
  few and set-based. Measured in Etapa 9 against the 20,000-card seed.
- The test suite runs against a real Postgres container, as uselets runs against DynamoDB Local.
