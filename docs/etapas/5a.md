# Etapa 5a — Formulários, automações e Slack

A primeira de três partes da Etapa 5 (escopo-mvp 4.1–4.5). Fecha três critérios do corte: o
formulário do REQ, a automação REQ → PRD com aviso no Slack, e a TEC → PRD. Decisões de Stênio em
2026-10-17; eventos e fila no ADR-0014.

## Entrega

| O quê | O que existe |
|---|---|
| Formulários (4.1) | Aba **Formulários** no espaço. O admin monta perguntas e escolhe para onde vai cada resposta: título, descrição (cada pergunta vira uma seção), prioridade, data limite ou um campo customizado. Também define o tipo, o estado inicial e as labels automáticas. Cada formulário tem um link (`/formularios/:id`): **quem só lê o espaço envia**, vira relator e recebe a chave do card criado |
| Automações (4.2) | Aba **Automações**: cada regra lida como frase (“Quando um card vai para … → Cria um card em PRD…”), ligar e desligar, **Execuções** com o resultado de cada uma. Editor **Quando → Se → Então**. **Gatilhos:** card criado, mudou de estado (para um estado ou para um grupo de estado), campo alterado. **Condições:** tipo, label, prioridade. **Ações:** criar card em outro espaço (e vincular), mudar estado, mover cards vinculados (e comentar neles), comentar, publicar no Slack |
| REQ → PRD (4.3) | Semeada: Requisição em “🚨 Itens priorizados” cria a Oportunidade no PRD (Backlog), vinculada por **entrega**, e publica no `#product_updates` |
| TEC → PRD (4.4) | Semeada: card do TEC num estado **concluído** leva os cards do PRD que ele **entrega** para “Preparando para lançar” e comenta neles |
| Slack (4.5) | Tela **Integrações**: o admin da organização conecta canais por *Incoming Webhook*. O endereço nunca volta pela API (só `hooks.slack.com/…1234`) |
| Quem age | As mudanças aparecem no histórico como **Automação**. Uma regra só alcança um espaço onde quem a criou pode escrever, conferido a cada execução. O que uma automação muda não dispara outra regra |
| Eventos (ADR-0014) | O histórico de auditoria é o outbox. Um despachante a cada minuto publica no barramento, e cada consumidor tem fila, DLQ e alarme. Localmente, cada escrita drena no próprio processo e o Slack é impresso no console |

API:
- Formulários: `/spaces/{id}/forms`, `/forms/{id}` e `/forms/{id}/submissions`.
- Automações: `/spaces/{id}/automations`, `/automations/{id}` e `/automations/{id}/runs`.
- Slack: `/integrations/slack/channels`.

Infra: as Lambdas `consumers/dispatch` (agenda) e `consumers/automation` (SQS), a regra no barramento,
a DLQ com alarme e a migração `0007_intake`.

No seed:
- o formulário **Pedido para Produto** no REQ, com o campo *Área solicitante*;
- o canal `#product_updates`, com um webhook de exemplo que só é impresso;
- as duas regras do corte.

## Demonstração

Com `bun run up`:

1. Entre como `rui@uselets.com`, que só lê o REQ. Vá em **Requisições → Formulários → Abrir**,
   preencha e clique em **Enviar**. A tela mostra a chave do card criado.
2. Entre como `admin@uselets.com` e abra esse card. No botão de estado, escolha **🚨 Itens
   priorizados**.
   - O console do `up` imprime `slack → hooks.slack.com: … foi priorizado e virou PRD-…`.
   - O **Discovery Board** ganha a Oportunidade, vinculada por *entrega*.
3. Em **Requisições → Automações → Execuções**: aparece “Executou · Criou PRD-… · Publicou no Slack”.
4. No **Delivery Board**, vincule um card que *entrega* essa Oportunidade e leve o card para
   **CONCLUÍDO**. A Oportunidade vai para *Preparando para lançar*, com um comentário da
   **Automação**.

Testes que cobrem a etapa:
- `bun run web:e2e`: `intake.spec.ts`;
- `intake.integration.test.ts`: a API, o Slack por MSW, a idempotência e o anti-laço.

**Pronto quando:** um envio do formulário do REQ cria o card com `business-form`; ao ir para “🚨 Itens
priorizados”, uma automação cria a Oportunidade no PRD, vincula as duas e publica no Slack; concluir o
card do TEC atualiza o PRD vinculado. Coberto por `intake.integration.test.ts` e `intake.spec.ts`.
