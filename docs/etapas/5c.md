# Etapa 5c — Tokens de API e webhooks de saída

A terceira e última parte da Etapa 5 (escopo-mvp 4.7, 4.8). Decisões de Stênio em 2026-10-17, no
ADR-0015.

## Entrega

| O quê | O que existe |
|---|---|
| Token pessoal (4.8) | Em **Meu perfil** (link no nome, no rodapé do menu): **Novo token**, com nome e validade (30, 90 ou 365 dias, ou sem validade). O valor `jia_…` aparece **uma vez**, com **Copiar**. A lista mostra o começo do token, a situação (ativo, revogado ou vencido), o último uso e o botão **Revogar** |
| Contas de serviço (4.8) | Em **Integrações**, só para o admin da organização: **Nova conta de serviço**, que é um membro do tipo agente. Ela recebe papéis em **Pessoas e papéis** como uma pessoa, e cada token dela age com esses papéis. É o que o MCP e os agentes da Etapa 6 vão usar |
| API com token | As mesmas rotas, sob `/v1`, com `Authorization: Bearer jia_…`. A resposta é 401 para token desconhecido, revogado, vencido ou de membro desativado. Um token não cria outro |
| Webhooks (4.7) | Aba **Webhooks** no espaço, só para quem o administra. Cada webhook tem nome, endereço `https`, eventos (card criado, alterado, movido, comentário) e liga/desliga. O segredo aparece uma vez, na criação, e **Novo segredo** troca por outro |
| Envio | Um JSON assinado (`x-jiraia-signature: t=…,v1=HMAC-SHA256`) com o evento, o card como está agora, quem fez e o que mudou. Um envio por webhook e evento |
| Retentativa | Retenta depois de 1, 5, 30, 120 e 360 minutos; depois disso a entrega falha. **Entregas** mostra a situação, as tentativas, o último HTTP, a próxima tentativa e **Reenviar** |
| Segurança | Só endereço `https` público: sem credencial na URL, sem nome interno e sem IP privado ou de loopback |

API:
- Tokens: `/me/tokens`, `/api-tokens/{id}` (DELETE revoga), `/service-accounts` e
  `/service-accounts/{memberId}/tokens`.
- Webhooks: `/spaces/{id}/webhooks`, `/webhooks/{id}`, `/webhooks/{id}/secret`,
  `/webhooks/{id}/deliveries` e `/webhooks/{id}/deliveries/{deliveryId}/retry`.

Infra:
- Rota `/v1/{proxy+}` sem autorizador.
- Lambda `consumers/webhooks`, com fila, DLQ e alarme.
- Lambda `consumers/webhook-retry`, agendada a cada minuto.
- Migração `0009_webhooks-and-tokens`.

Localmente, cada entrega é impressa no console e respondida com 200; `LOCAL_WEBHOOKS=1` envia de verdade.

## Demonstração

`bun run up`:

1. Como `admin@uselets.com`, clique no seu nome no rodapé → **Novo token** → copie o valor.
   `curl -H "Authorization: Bearer <token>" localhost:8280/work/v1/me` responde com você. Depois de
   **Revogar**, a mesma chamada responde 401.
2. **Discovery Board → Webhooks → Novo webhook** para `https://erp.example.com/jiraia`, com
   *Comentário*. Copie o segredo. Comente num card. O console mostra
   `webhook → https://erp.example.com/jiraia card.commented …`, e **Entregas** mostra *Entregue*.
3. Em **Integrações → Nova conta de serviço**, crie "Rotina de roadmap". Em **Pessoas e papéis** do
   espaço, dê a ela o papel Membro e crie um token para ela.

Testes que cobrem a etapa:
- `bun run web:e2e`: `outward.spec.ts`;
- `outward.integration.test.ts`: tokens, contas de serviço, assinatura, retentativas, entrega única e
  endereço interno.

**Pronto quando:** um programa age na API com um token pessoal ou de conta de serviço, com os papéis
do dono, e perde o acesso ao ser revogado; um sistema externo recebe as mudanças de cards, assinadas,
e as tentativas continuam até ele responder — `outward.integration.test.ts` e `outward.spec.ts`.
